# ADR 0008: Recording in the browser, and one upload path for every source

- Status: Accepted
- Date: 2026-10-07

## Context

A visit starts from audio. The web app offers three ways to supply it: record it with the microphone, upload a file, or take one of the bundled sample consultations.

The API sets the frame. It accepts one file of at most 4 MB and five minutes, holds it in memory for one request and never stores it (ADR 0003). It decides what the file is from its bytes, not from what the client declares.

The browser has to stay inside that frame on its own:

- Browsers do not agree on what `MediaRecorder` produces. Chrome, Edge and Firefox record Opus in a WebM container. Safari recorded only AAC in MP4 for years and added WebM later.
- A person recording needs to see that the microphone is picking something up, and how much time is left.
- An upload on a slow connection can take half a minute, which is too long for a spinner with no information.

## Decision

**The recording format is negotiated when recording starts.** The app asks the browser for the first format it supports from a fixed list: Opus in WebM, Opus in Ogg, then AAC in MP4. Opus comes first because it is designed for speech at low bitrates. The bitrate is 32 kbps, which keeps speech clear and makes a full five-minute recording about 1.2 MB.

**The five-minute limit is enforced by a timer in the browser.** A recording that reaches it is stopped and kept, with a notice. The length the browser measured is sent with the upload.

**Audio stays in memory.** A recording, a chosen file or a sample is a `Blob` in the page until it is uploaded. It is not written to `localStorage`, IndexedDB or any other storage. Reloading the page discards it, and the page warns before that happens.

**Consent comes before the microphone.** Pressing the record button, or creating a note from a file or a sample, first opens a dialog that asks whether everyone in the conversation has agreed. Nothing is recorded or sent until the answer is yes, and the dialog opens with the focus on "Cancel", so a stray Enter cannot confirm it. The question is asked once per visit. The API enforces consent separately and refuses to process a visit without it.

**All three sources end up as the same thing.** Each produces a `SelectedAudio`, which goes through the same checks and the same upload. Files and samples are checked in the browser for type, size and length before any of it is sent. Those checks only save a round trip: the API makes its own decision.

**Nothing identifying is sent that is not needed.** The uploaded part gets a neutral file name, and the suggested visit title never comes from a file's name.

**The waveform is drawn in the browser.** An `AnalyserNode` reads the microphone's level, and a canvas draws one bar per moment. It is not connected to the speakers, and nothing is sent anywhere to produce it.

**The upload uses `XMLHttpRequest`.** It is the only API that reports upload progress in every browser, and it also exposes the response as it arrives, so the same request carries the progress events of the run. Every other call uses `fetch`. Both go through one HTTP client, so errors and session renewal behave the same.

**The visit is created first, and the recording is then uploaded to it.** A retry reuses that visit. Abandoning the attempt deletes it, so a failed attempt leaves no empty visit behind.

## Alternatives considered

- **Record uncompressed audio and upload a WAV file.** The same format in every browser. Five minutes of speech-quality PCM is close to 10 MB, more than twice the upload limit.
- **Ship an Opus or MP3 encoder as WebAssembly.** One format everywhere, at the cost of a large download and a worker, to replace something the browser already does.
- **`fetch` with a streaming request body.** It can report upload progress, but only in Chromium browsers and only over HTTP/2.
- **`fetch` without progress.** Simpler, and it leaves the user with no information for the longest wait on a slow connection.
- **Keep an unsent recording in IndexedDB so a reload does not lose it.** That writes audio to disk, which this project rules out.
- **Chunked or resumable uploads.** Not needed below 4 MB.

## Consequences

- The uploaded format depends on the browser. The API already identifies formats from the bytes, so nothing else changes.
- Chrome's WebM/Opus recordings were transcribed correctly by Gemini on 2026-10-07. Recording in Safari and Firefox has not been tried. AAC in MP4, which is what an older Safari records, works as an uploaded file.
- An unsent recording is lost on reload. That is the price of never storing audio.
- The length of a recording is what the browser reports. The limit the server can enforce itself is the file size.
- One request in the app is not made with `fetch`. It is isolated in one module with its own tests.
- The sample consultations are synthetic speech, generated by `apps/web/scripts/make-samples.mjs`, and add about 370 KB to the repository.
